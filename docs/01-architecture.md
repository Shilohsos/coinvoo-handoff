# 01 — Architecture

---

## 1. Shape

One Node service. No workers, no queues, no containers, no external database.

```
                     ┌─────────────────────────────────────────────┐
Ad click ───────────►│  GET /c/:token            (Caddy → :8770)   │
                     │    ├ store click row                        │
                     │    └ 302 → t.me/<bot>?start=c_<click_id>    │
                     └─────────────────────────────────────────────┘
                                    │
                                    ▼
                     ┌─────────────────────────────────────────────┐
                     │  Gate bot (gatebot1 / brand-two-onboard)          │
                     │    /start c_<click_id>                      │
                     │      ├ POST /api/join  ─────────────────────┐│
                     │      └ DM welcome + personal offer link     ││
                     └─────────────────────────────────────────────┘│
                                                                    │
                     ┌──────────────────────────────────────────────▼┐
                     │  POST /api/join                               │
                     │    ├ upsert member (brand, telegram_id)       │
                     │    ├ bind member.click_id = click_id          │
                     │    └ append attribution_log                   │
                     └───────────────────────────────────────────────┘

IQ Option registration / deposit
        │
        ▼
Affstore postback ──► ┌───────────────────────────────────────────────┐
                      │  GET|POST /api/aff        (Caddy → :8770)     │
                      │    1 store raw event  (immutable, dedupe id)  │
                      │    2 match  afftrack → trader_id → click_id   │
                      │    3 write attributions + attribution_log     │
                      │    4 forward to Joinvoo (parallel run)        │
                      │    5 return {ok:true} immediately             │
                      └───────────────────────────────────────────────┘
                                    │
                                    ▼
                      ┌──────────────────────────────┐
                      │ Dashboard  /dash (basic auth)│
                      │ Daily Telegram report        │
                      └──────────────────────────────┘
```

**Principle:** the redirect path and the postback path must never wait on anything except one SQLite write. Matching, forwarding, rollups and reporting all happen after the HTTP response is sent (on the same event loop, in a `setImmediate`, or on the retry worker's next tick).

## 3. Request flows

### 3.1 Click (Path A)

```
GET /c/7K2M9QX4AB?campaign=NG_Broad&adset=Broad_18-34&ad=vid_03&ttclid=E.C.P...
  → 302 Location: https://t.me/gatebot1bot?start=c_7K2M9QX4AB
```

- The token is the click id. It is base32 (Crockford alphabet, no `I L O U`), 10 characters, generated by `crypto.randomBytes`.
- Telegram payload = `c_` + click id → 12 characters, far below the 64-character limit.
- Unknown token → `404` with a plain text body, no redirect.
- Query parameters are the ad context. Missing ones are stored as `NULL`, never as empty strings.
- `ttclid`/`fbclid`/`gclid` are stored verbatim for the ad platforms' own matching.
- IP is never stored raw: `ip_hash = sha256(ip + IP_SALT)`, first 32 hex characters.
- The redirect is issued before any auxiliary work. Target: p99 under 300 ms.

### 3.2 Join

Two sources, one table:

1. **Payload join** — gate bot receives `/start c_<click_id>` and calls `POST /api/join` with `{click_id, telegram_id, username, first_name, source:"bot:start"}`.
2. **Channel join** — gate bot approves a join request and calls the same endpoint with `{click_id:null, telegram_id, …, source:"channel:<channel_id>", channel_join:true}`.

`members` is unique on `(brand_id, telegram_id)`. A second call for the same pair updates `username`/`first_name` and only fills `click_id` if it is currently `NULL` (first touch wins; a later click does not overwrite an existing attribution).

### 3.3 Postback

```
GET /api/aff?status=ftd&net=affstore&trader_id=197512345&amount=50&currency=USD
             &country_code=NG&event_id=uuid&clickid=&afftrack=7000000001&aff_model=revenue
```

1. Normalise `status` → `reg | ftd | dep` (see `docs/03-attribution-rules.md §6`).
2. `INSERT OR IGNORE` into `events` with the complete raw payload. If the `event_id` already exists → return `{ok:true, duplicate:true}` and stop.
3. Resolve the member (rules in `03`). Write `attributions` and an `attribution_log` line either way.
4. `setImmediate`: forward to Joinvoo (parallel run) with the resolved `tg_id` if we have one; record the attempt.
5. Respond `{ok:true, matched:true|false, path:"afftrack"|"trader_id"|"click"|"parked"}`.

The response is **not** contingent on the Joinvoo forward. If Joinvoo is down, the event is still stored and matched; the forward is retried by the worker.

### 3.4 Retry worker

One `setInterval` at 60 s with a `busy` guard:

- picks up `events.state='parked'` younger than `PARK_HOURS` (48 h) → re-runs the matcher;
- picks up `events.forward_state='pending'` → re-attempts the Joinvoo forward with exponential backoff (1, 2, 4, 8, 15, 30 min, then hourly);
- expires parked events older than 48 h → `state='expired'`, still forwarded unattributed;
- rebuilds `daily_rollup` for today and yesterday.

## 4. Design decisions

| # | Decision | Why |
|---|---|---|
| D1 | **Zero dependencies** — `node:http` + `node:sqlite` | Host is at 96 % disk; every existing bot has been broken at least once by a build/dependency mismatch. A dependency-free service cannot rot, and `node --check` is a complete safety check. |
| D2 | **One process, one database file** | Volume is a few thousand rows a month. Splitting into services would add failure modes for zero benefit. |
| D3 | **SQLite in WAL mode** | Concurrent reads from the dashboard while the postback path writes. `PRAGMA busy_timeout = 5000`. |
| D4 | **Raw event stored before interpretation** | So that a matcher bug is always re-runnable against history. The raw payload is never updated. |
| D5 | **Append-only attribution log** | Every decision, including rejected candidates, is recorded. This is the audit trail for money. |
| D6 | **First-touch click wins** | A member is attributed to the click that brought them in. Later clicks from the same person do not rewrite history; they appear in `clicks` as their own rows. |
| D7 | **Parallel forward to Joinvoo** | We must be able to reconcile our numbers against theirs for a week before cancelling. Coinvoo forwards; it never withholds. |
| D8 | **Port 8770, `/api/aff*` repointed in Phase 2** | `aff-recon` owns 8769 today. Phase 2 puts coinvoo behind `/api/aff*` and leaves `aff-recon` as a fallback until one week of reconciliation. |
| D9 | **Server-rendered dashboard, no build step** | A single `render()` per screen returning an HTML string. No bundler, no assets pipeline, no CSP problems. |
| D10 | **Display in `Africa/Lagos`, store UTC ms** | Master reads WAT; the machines think UTC. Never mix the two in storage. |
| D11 | **No `?start=` payload on the main trading bot in v1** | The money path (`iqbot-v3`) is not touched. The gate bots capture the payload; from there the member is pushed into the channel and the trading bot as normal. |

## 5. Failure modes and what happens

| Failure | Behaviour |
|---|---|
| SQLite write fails (locked) | Retry once after 50 ms; then HTTP 500 JSON; the client (Caddy / ad platform) shows an error. Event loss is visible in `GET /api/aff/stats`. |
| Joinvoo unreachable | Event is matched and stored; forward marked `pending`; retried by the worker. |
| Gate bot cannot reach coinvoo | Bot logs the failure and continues its normal welcome flow; the join is recorded by the bot's own DB and can be back-filled in Phase 2 from `gatebot1.db`. |
| Telegram payload missing (`/start` with no payload) | Member created with `join_source='organic:bot'`. |
| Duplicate postback (`event_id` repeated) | `{ok:true, duplicate:true}`; counted once. |
| Same broker account, second Telegram id | Attributed to the account owner; the second Telegram id is logged as a candidate and rejected with reason `account_claimed`. |
| Postback for a trader id we have never seen | Parked, retried for 48 h, then expired and forwarded unattributed. |

## 6. What this service is *not*

- Not a landing-page builder.
- Not an ad-spend API client in v1 (manual entry; Phase 5 adds the read API, TikTok pull is P2).
- Not a chat/team inbox.
- Not a link shortener with public signup — there is no user-facing surface at all except the dashboard.
